# 大型项目能力评估（LARGE PROJECTS）

> 结论先说：**这套团队具备大型项目的“组织骨架”和“交付纪律”，但不是开箱即用的大型项目交付平台。**  
> 对 5–15 人等效工作量、3–12 个月、多模块的产品，经过 1–2 个迭代校准可以支撑；  
> 对 50+ 人等效、多团队、强合规、跨年的项目，需要补齐本文第 5 节的规模化能力。

## 1. 成熟度定位

| 等级 | 特征 | 当前 |
|---|---|---|
| L1 临时 | 靠个人经验，无标准流程 | — |
| L2 可重复 | 有角色、模板、基本门禁 | ✅ 已超过 |
| L3 已定义 | 标准流程、职责边界、证据标准 | ✅ **当前主水平** |
| L4 量化管理 | 指标、成本、质量、容量可度量并用于决策 | ⚠️ 部分（缺自动化度量） |
| L5 持续优化 | 流程自动适应、数据驱动改进 | ❌ 未达 |

**判断**：流程定义达到 L3；执行能力在 L2–L3；规模化编排、成本治理、组合管理仍在 L2 左右。

## 3. 已经具备的大型项目机制

这些不是口号，是团队文件里可执行的机制：

1. **T4 Critical 轨道**（`.opencode/agents/ai-team/chief.md`）
   - 威胁建模、合规、性能/容灾、UAT、灰度/回滚演练。
2. **G0–G8 阶段门禁**（`docs/WORKFLOW.md`、`ai-team-standards/references/QUALITY-GATES.md`）
   - 每个阶段有出口标准，禁止“大爆炸式”集成。
3. **任务 DAG + 单一 owner + 文件所有权**（`chief.md` §5–§6）
   - 支持多 engineer 实例按模块并行，避免同文件冲突。
4. **持久项目记忆**（`.ai-team/state/**`）
   - PROJECT/STATUS/TASKS/DECISIONS/RISKS/HANDOFF/RUN_LOG，支持跨会话、跨天推进。
5. **独立审查/测试/安全**
   - 审查者不改代码；QA 独立验证；安全审计员独立放行。
6. **证据标准**
   - 命令 + 退出码 + 原始输出 + 文件路径；没有证据不算完成。
7. **技术栈无关**
   - `STACK-PLAYBOOK.md` 覆盖 Node/Python/Go/Rust/Java/.NET/Ruby/PHP/移动端/C++/数据/AI/基础设施。
8. **发布工程**
   - `ai-team-release` 提供 Docker/Compose/K8s/CI/回滚/可观测性模板。
9. **AI 功能工程**
   - `ai-team-ai-native` 提供 eval、RAG、Agent 工具权限、guardrails、成本/隐私。
10. **团队成长机制**
    - `.ai-team/team/GROWTH.md` 提案、证据 ≥2 次、用户批准后才改团队。

## 4. 规模化缺口（按影响排序）

### 4.1 编排是单点，不是持久系统

当前 Chief 是一个会话内的编排者：

- 没有任务队列、调度器、自动重试、失败恢复；
- 长任务靠 `HANDOFF.md` 人工续跑；
- 多 workstream 并行依赖模型/harness 的 subagent 能力；
- 没有 merge queue / 集成列车。

**影响**：项目越大，Chief 的上下文和调度越容易成为瓶颈。

### 4.2 缺代码库智能

- 没有语义索引、依赖图、调用图、影响面分析；
- 大 monorepo 只能靠 grep/read，容易漏改、重复改；
- 没有 affected-only 测试选择，CI 会越来越慢。

**影响**：10 万行以上代码库的修改效率和正确性下降。

### 4.3 缺组合/项目群管理

- PM 管产品，Chief 管单项目交付；
- 没有 program manager 管多项目依赖、里程碑、预算、人力；
- 没有跨团队接口人/工作流负责人。

**影响**：多团队并行时，依赖和资源冲突靠人肉协调。

### 4.4 专家深度不足

当前是 1 个通用工程师角色，可并行多实例，但缺少：

- 前端/后端/移动端/数据/ML/SRE/性能/合规等专家角色；
- 领域专家（支付、医疗、工控等）。

**影响**：超大项目需要更深的技术判断和领域合规。

### 4.5 环境与运维仍是模板级

- 有一键部署/回滚模板，但没有真实环境 provisioning；
- 没有 secrets 生命周期、证书、DNS、网络策略的自动管理；
- 没有 on-call、事故指挥、SLO 错误预算执行。

### 4.6 合规/审计不是正式系统

- 证据是 Markdown，不是不可篡改审计日志；
- 没有 SOC2/ISO 27001/GDPR/等保的 control mapping；
- 没有数据分类/驻留/保留的自动执行。

### 4.7 成本/资源治理缺失

- 没有每任务 token/成本预算；
- 没有模型路由（小模型做简单任务）；
- 没有并发配额/速率限制；
- 大项目容易“质量上去了，成本失控”。

### 4.8 生态集成缺失

- 没有 Jira/Linear/GitHub/GitLab/Slack/飞书连接器；
- PR、工单、通知、文档站需要人工搬运；
- 没有组织级知识库/代码搜索。

### 4.9 量化度量缺失

- 有门禁记录，但没有自动 DORA/质量/成本看板；
- 无法回答“这个团队这个月交付效率如何、缺陷逃逸率多少、每次交付成本多少”。

## 5. 规模化升级路线

### P0：支撑 20–50 人等效项目（必须先做）

1. **Program Manager 角色**
   - 多项目路线图、跨 workstream 依赖、里程碑、预算/人力、风险组合。
2. **Workstream Lead 机制**
   - 每个 workstream 一个 lead（可以是 engineer 实例），对模块交付负责。
3. **持久编排**
   - 任务队列 + 状态机 + 自动重试 + 定时/事件触发；Chief 从“会话编排”升级为“可恢复编排”。
4. **代码库索引**
   - 依赖图、符号索引、影响面分析、affected-only 测试选择。
5. **合并队列/集成列车**
   - 小步合并、自动 rebase、按序验证、失败自动回退。
6. **成本治理**
   - 每任务 token/成本预算、模型分级路由、并发配额、成本看板。

### P1：支撑 50–150 人等效项目

1. **专家 agent 包**：frontend/backend/mobile/data/ML/SRE/performance/compliance。
2. **CI 质量门禁**：覆盖率（变更行/关键路径）、架构 fitness、契约兼容、性能预算、flaky 隔离。
3. **环境自动化**：IaC provisioning、secrets 生命周期、证书/DNS、预览环境。
4. **事故/on-call**：SLO/错误预算、告警路由、事故指挥、复盘模板。
5. **集成连接器**：Jira/Linear、GitHub/GitLab PR、Slack/飞书、文档站。

### P2：支撑 150+ 人/强合规/跨年项目

1. **合规包**：SOC2/ISO 27001/GDPR/等保 control mapping、不可篡改审计、数据驻留。
2. **组合看板**：DORA、逃逸缺陷、周期时间、成本/交付、容量。
3. **组织级知识库**：代码搜索、ADR/契约/runbook 索引、权限感知。
4. **正式治理**：变更委员会、风险接受矩阵、供应商/外包管理。

## 6. 用当前团队跑大型项目的现实打法

如果现在就要做一个大型项目，不需要等 P0 全部完成，按下面方式用：

1. **判 T4**，不要降级。
2. **拆 3–7 个 workstream**，每个有：
   - 明确模块/文件所有权；
   - 一个 lead engineer；
   - 自己的 `.ai-team/state/HANDOFF.md` 片段；
   - 独立的验收与证据。
3. **先冻结契约**（API/事件/数据），再并行实现。
4. **每周集成**，不要月末大合并；每次集成都跑门禁。
5. **一个 workstream 同一时间只有一个 writer**；冲突走 merge/rebase + 重跑测试。
6. **里程碑门禁**：每个里程碑都写 `REVIEW_LOG`/`STATUS`，不通过不进入下一里程碑。
7. **成本预算**：给每个 workstream 设 token/时间预算；超预算先降范围/换小模型。
8. **生产发布**：永远 L3 人工批准；灰度 + 回滚 + 监控窗口。
9. **跨会话**：每个 workstream 结束写 HANDOFF；不要靠聊天历史。
10. **人机分工**：人负责目标、优先级、风险接受、生产批准；团队负责分析、实现、验证、证据。

## 7. 最终判断

| 项目规模 | 判断 |
|---|---|
| 1–5 人等效、1–3 个月 | ✅ 直接可用，甚至流程偏重（用 T1/T2） |
| 5–15 人等效、3–12 个月、多模块 | ✅ 可用；建议 1–2 个迭代校准 |
| 15–50 人等效、多 workstream | ⚠️ 可用，但建议先补 P0（program manager、编排、代码索引、成本） |
| 50–150 人等效、多团队 | ⚠️ 需要 P0 + P1；当前团队是“操作系统”，不是“交付平台” |
| 150+ 人等效、强合规、跨年 | ❌ 不能开箱即用；需要 P0+P1+P2 + 正式治理 |

**一句话**：它已经是一个**能打大型项目的中枢神经系统**，但还不是**大型项目的基础设施**。  
把它用在大型项目上是合理的，前提是：T4、拆 workstream、冻契约、周集成、成本预算、人工治理——以及按需补 P0。
